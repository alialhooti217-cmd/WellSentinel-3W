# 🧾 Model Card: WellSentinel-3W v1.0

All numbers come from [`reports/final_results.json`](../reports/final_results.json) (generated by
`scripts/09_results_table.py`). Experiment history: [`WORK_LOG.md`](WORK_LOG.md) (E00–E10).

## Intended use
- **What it is for:** decision support for production and flow-assurance engineers. It flags windows where a well
  is likely in an undesirable state (hydrate, valve closure, scaling, instability, …), suggests the event type and
  shows which sensors drove the alarm.
- **What it is not:** a safety system. It must not replace SIS/ESD logic, trip settings, or an operator's
  judgement, and it is not validated for automatic control actions.
- **Users:** control-room and production engineers; students and reviewers studying honest evaluation on 3W.
- **Out of scope:** wells, fields or lift methods unlike the Petrobras 3W wells without re-validation; the event
  types that the evaluation below shows it cannot recognise.

## Model
| Item | Value |
|---|---|
| Version | v1.0 (`models/wellsentinel_v1.joblib`), experiment E10 |
| Algorithm | scikit-learn `HistGradientBoostingClassifier` (300 iterations, learning rate 0.08, 31 leaves, L2 0.1, class-balanced, NaN-native) |
| Inputs | 15-min windows every 5 min of the 27 3W variables (1 Hz) → 145 features: 6 statistics per sensor (mean, std, min, max, last, slope), oscillation of P-TPT / P-MON-CKP / P-PDG (FFT power share, RMS amplitude and dominant period in a 2–60 min band over a 120-min causal history) and live drift of 4 pressures (window mean − mean over [t−3h, t−1h]) |
| Output | probability per class (Normal + 9 events) → P(abnormal) = 1 − P(Normal) |
| Alarm | P(abnormal) ≥ 0.5 for 2 consecutive windows (alarm-flood control) |
| Explanation | per-window sensor occlusion: each physical sensor's features are set to a typical healthy window's values; the drop in P(abnormal) is that sensor's contribution |

## Training data
- Petrobras 3W v2.0.0 (CC BY 4.0): 2,228 instances (real, simulated, hand-drawn), 27 variables, 10 classes.
- **Deployable model:** all 40 real wells + all simulated + all hand-drawn instances.
- **Evaluation models:** 5-fold cross-validation **grouped by well** (`StratifiedGroupKFold`); a well never appears in
  both training and test; simulated and hand-drawn instances are used for training only.

## Evaluation (unseen wells, 5-fold grouped cross-validation, 481 real event instances)
| Metric | Baseline v0.1 | **v1.0** |
|---|---|---|
| Macro-F1 (mean ± std over folds) | 0.317 ± 0.166 | **0.337 ± 0.163** |
| Balanced accuracy | 0.362 ± 0.142 | **0.375 ± 0.139** |
| Strict event detection rate | 40.5 % | **50.5 %** |
| Strict early-warning rate | 5.6 % | **8.3 %** |
| Median strict detection delay | 5 min | **5 min** |
| False alarms per well-day | 3.0 | **1.7** |

*Strict:* the alarm must be off when the event starts and then fire. v1.0 is better than the baseline on strict
detection in 4 of 5 folds and has 43 % fewer false alarms per well-day. Macro-F1 differs between folds from
0.10 to 0.55 (well mix matters more than the model).

**Leakage check:** the same model with a random window-level split scores 0.983 ± 0.008 macro-F1, 2.9× the
unseen-well score. Random-split numbers are not valid estimates for a new well.

**Per class (v1.0):** hydrate in production line F1 0.89 (strict detection 79 %, see caveat), spurious DHSV
closure 0.53 (77 %), Normal 0.71, flow instability 0.17 (51 %), scaling in PCK 0.15 (14 %); severe slugging,
BSW increase, PCK restriction and rapid productivity loss F1 0.00. Full table:
[`reports/final_results.md`](../reports/final_results.md).

## What the model relies on
- Top sensors (permutation importance on unseen wells, grouped by physical sensor): Xmas-tree temperature,
  temperature upstream of the production choke, Xmas-tree pressure (incl. its oscillation), downhole pressure,
  gas-lift rate. Operator signals (valve states, gas-lift rate, choke openings) carry 9 % of the importance.
- In process terms: mostly the **"flow stopped / well cooling"** signature, plus oscillation power for
  instability-type events.

## Limitations and data caveats
- **Instrumentation fingerprint (hydrate):** T-MON-CKP has data on only 9 of 40 wells and in every
  hydrate-in-production-line window. Without it hydrate F1 falls 0.89 → 0.77; with only sensors present on most
  wells it falls to 0.50. Hydrate results must always be quoted with this caveat.
- **Gas-lift trips:** many hydrate alarms are driven by the gas-lift rate dropping to zero at onset, a valid
  physical trigger but an operator/equipment action rather than the hydrate itself.
- **Severe slugging:** 31 of 32 real instances come from one well (WELL-00014), so it is effectively tested on one
  fold, and the model never identifies it (F1 0). Simulated slugging differs from real slugging (cycle ≈ 51 vs 80 min).
- **Rare events:** BSW increase (4 real instances), PCK restriction (6), productivity loss (11) and hydrate in
  service line (13) are too rare to learn or to evaluate reliably.
- **Early warning is rare** (8.3 % strict): most alarms come after onset; temperatures react to consequences.
- **Labels:** 3W instances are cut by Petrobras around events; features that compare with the start of a file
  can learn this cut rather than physics (rejected in E04).
- **Generalisation:** trained on Petrobras offshore wells only; other fields, completions (e.g. ESP wells) and
  lift strategies need re-validation before use.

## Ethical and operational considerations
- **Alarm fatigue:** 1.7 false alarms per well-day is still above the ≤ 1 target; tune threshold and persistence
  with operations staff, ideally on a cost curve (missed event vs. false alarm).
- **Humans in the loop:** any intervention decision stays with qualified engineers.
- **Transparency:** every alarm can be explained in the dashboard; the explanation can reveal shortcuts
  (missing sensors, operator actions), and that is intended.
